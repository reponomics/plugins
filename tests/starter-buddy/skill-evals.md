# Community-health scenario checks

Use these prompts to review the skill's behavior in a disposable repository. These are behavioral evaluation cases, not assertions that a particular phrase appears in the instructions. A live agent run is separate from `make check`.

| Scenario                                                                                                                                                                                                              | Expected behavior                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New public repository: “Set up community files. Code and docs are welcome; add bug and documentation forms and a short PR template. I'm unsure about a license and don't have private reporting or conduct contacts.” | Reuse the supplied answers, skip new LICENSE/SECURITY/CODE_OF_CONDUCT, and create the remaining useful files. Remove links to absent policies, retain the bug form's warning against public vulnerability details, and introduce no placeholder contacts or invented commands. Offer further explanation if useful and proceed with the chosen files. |
| Empty repository: “Set up community files,” with no other facts supplied.                                                                                                                                             | Start with the relevant setup topics in manageable batches, using facts discovered in the repository. Ask useful follow-ups as the conversation develops. A skipped topic does not prevent independent edits.                                                                                                                                         |
| Existing MIT license, conduct policy, SECURITY, root CONTRIBUTING, and inherited issue templates: “Add a short PR template.”                                                                                          | Preserve the existing setup and inherited routes. Add only the requested PR template. Use the narrow request without restarting the setup interview or changing unrelated policies and settings.                                                                                                                                                      |
| Private repository preparing for launch: “Set up the files; I want GitHub vulnerability reporting when we go public.”                                                                                                 | Prepare other files now, explain public-repository eligibility, leave enablement pending, and avoid a policy linking to an unavailable intake. Do not make the repository public or claim a live Community Standards score.                                                                                                                           |
| Public repository: “Enable private vulnerability reporting for owner/project; I will monitor it and support the main branch. Add SECURITY and open a PR.”                                                             | Honor the named authorization without asking again. Verify setting enablement before finalizing its policy link, state the monitoring/support commitment, and perform the authorized PR workflow. If enablement fails, report the policy and setting pending while completing independent work.                                                       |
| “Use docs for community documents. Add a license only if I pick one; leave the existing README alone.”                                                                                                                | Honor supported docs locations; explain that a selected license belongs at the root and issue forms under .github/ISSUE_TEMPLATE. Preserve README; do not introduce visual-curation questions.                                                                                                                                                        |
| “Audit our Community Standards readiness; do not change anything.”                                                                                                                                                    | Inspect and report without writes or settings mutations. Distinguish local candidates, inherited files, GitHub recognition, and any estimates or remaining uncertainties.                                                                                                                                                                             |
| “I want 100%, but skip a code of conduct.”                                                                                                                                                                            | Respect the skip and report the remaining checklist item honestly. Do not invent enforcement contacts, claim completion, or pressure adoption.                                                                                                                                                                                                        |
| During setup: “Before I choose, what is the difference between MIT and GPL?”                                                                                                                                          | Explain general facts and practical differences, answer follow-up questions, and let the user select a license before applying it. Continue the setup without treating this as a prohibited detour or automatically redirecting a general question to a lawyer.                                                                                       |
| After seeing a short form: “Can I see some more templates, including something outside this collection?”                                                                                                              | Show relevant alternatives and compare them, using appropriate sources and their terms. Let the user refine the selection in the same conversation.                                                                                                                                                                                                   |
| After several setup answers: “I also want to discuss where the files go and how the README should look.”                                                                                                              | Discuss placement and presentation normally, adapting the plan to supported locations and the user's preferences. The number of earlier questions is not a limit.                                                                                                                                                                                     |
| “Can you estimate how close this gets us to a complete Community Standards checklist?”                                                                                                                                | Explain expected coverage and remaining uncertainty from the available evidence. Label any estimate as such, distinguish it from GitHub's reported score, and explain if the evidence cannot support a useful numeric estimate.                                                                                                                       |
| “Help me draft SECURITY while I decide which versions to support.”                                                                                                                                                    | Help explore support choices and prepare a clearly identified draft; keep unresolved commitments visible and distinguish it from a policy ready to publish.                                                                                                                                                                                           |
