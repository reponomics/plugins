# Release Buddy skill evaluations

These cases test activation, scope, and useful decisions rather than link validity. They are a test plan, not evidence of successful runs. Use fresh sessions against disposable repositories, with and without the plugin. Supply the fixture facts and grade observed behavior against the expectations. Keep publication disabled; no case needs registry credentials or remote changes.

## Reproduce selected live checks

The opt-in [runner](run_skill_evals.py) supplies the fixed prompts and fixture READMEs in [skill_eval_cases.json](skill_eval_cases.json). It uses the configured Claude client and default model, records skill calls and requested source URLs, and measures response length without assigning semantic grades. The normal `make test` target does not invoke a model.

```sh
make eval-release-skills EVAL_CASES='combined-plan registry-boundary source-update' EVAL_OUTPUT=.cache/releases/mitigation-evals.json
make eval-release-skills EVAL_CASES='combined-plan artifact-verification' EVAL_REPEAT=2 EVAL_OUTPUT=.cache/releases/mitigation-repeats.json
```

Use the existing `VENV` and `CLAUDE` Makefile variables to select the environment and client. Omit `EVAL_CASES` to run all nine executable cases. Each case uses a fresh disposable directory, a 180-second timeout, and only skill invocation, reading, search within files, and web fetching tools. Results are saved after each run with the source revision, plugin-content digest, observed model/client, response, and tool calls. Select a different output path to retain an earlier run; the chosen output file is replaced.

Review content and source usage manually. A successful command, an appropriate skill call, or meeting a word budget is not enough to pass a case. A recorded web-fetch call proves a retrieval was attempted, not that the returned source was complete or correctly interpreted. The 200-word monorepo and 150-word bot-PR bounds are explicit user requirements; the other numerical bounds are reviewer diagnostics for prompts that ask for brevity without a number. In particular, verify that a short answer retains the necessary qualifications and that explicitly requested configuration is still provided. Compare repeated runs with the same prompt and fixture; keep failures as observations instead of discarding them. The runner covers a subset of the cases below, not every scenario or a no-plugin baseline. Its fixtures are README facts, not working signed repositories or build outputs: the new cases test planning and interpretation, not cryptographic execution. No live model runs are implied by adding or updating a case.

## Behavioral cases

| “Which versioning workflow fits this project?” Small Python package, two releases per year, curated changelog, working tag-derived version backend.                                                              | Activate release-versioning. Preserve the version source; consider manual version choice with CI publication, explain the recommendation's maintenance cost, and avoid adding a manifest bumper or Node tooling by default. No signing intake.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| “Automate our changelog, but let us review each release.” Project uses Conventional Commits and squash merges; no release tool yet.                                                                              | Recommend a compatible preparation flow such as release-please after checking ecosystem support. Check the messages that reach the release branch; distinguish release PR creation from publication, and identify the publishing step.                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| “Keep Changesets; improve our release notes.” Existing changesets and maintained version PR; signing is out of scope.                                                                                            | Retain Changesets and the current release control. Improve contributor summaries or changelog configuration, validate the selected behavior, and avoid a tool migration or integrity audit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| “Release these packages independently.” npm workspace with public A depending on public B and unrelated private C; only B changed.                                                                               | Establish independent version policy, inspect dependency and private-package behavior, and preview the affected release set and dependency ranges. Do not assume only B changes or publish C.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| “Should everything in this monorepo share one version?” A core SDK and adapters are upgraded together, but unrelated CLI tools have different consumers and cadences. No release tool selected.                  | Activate release-versioning and read monorepo guidance. Compare a shared unit, independent packages, and coordinated groups from the consumption pattern; consider an SDK group plus independent tools. Separate version relationship, cadence, and publication selection before recommending a product.                                                                                                                                                                                                                                                                                                                                                                       |
| “We publish monthly, so do all packages need the same version?” Separately consumed packages already have independent histories.                                                                                 | Explain that a coordinated release train can retain independent versions. Preserve working histories and identify package versions in the release record rather than equating schedule with version synchronization.                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| “Core has a breaking update; must every package get a major bump?” Adapter 3.4.0 depends on core `^1.2.0`; core becomes 2.0.0; formatter 5.0.0 is unrelated.                                                     | Evaluate the adapter's dependency range, adoption decision, and own public contract. Contrast the result with an explicitly chosen shared-version policy.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| “Only a private generator changed; nothing should release.” The generator changes code embedded in a public package, but no file under that package's source directory changed.                                  | Distinguish publishability from release impact. Inspect generated artifacts and package baselines, consider a public-package release, keep the generator private, and validate installation outside workspace links.                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| “Is removing this flag a patch?” CLI at 1.4.2; the removed flag is documented and used by consumers, but the commit says `fix:`.                                                                                 | Use release-versioning and identify the public compatibility break rather than accepting the label. | “Automate bumps for our 0.x library.” Existing policy increments minor for breaking changes; tool defaults differ.                                                                                               | Preserve or explicitly resolve the policy and test the chosen tool's configuration against a representative break. Do not claim SemVer mandates one `0.x` bump algorithm.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| “Publish release candidates without affecting stable installs.” Existing stable package and publisher, no preview channel.                                                                                       | Distinguish prerelease versions, hosted release flags, and registry channels. Settle promotion behavior and validate the intended version/channel without publishing. Consult integrity guidance only where the publishing change affects authority or guarantees; route unsupported registry implementation to the owning registry’s official documentation.                                                                                                                                                                                                                                                                                                                  |
| “Migrate from manual releases to release-please.” Last published version differs from the current unreleased manifest; an old tag workflow remains enabled.                                                      | Establish the actual release baseline and pending changes, preserve or deliberately map tags, and replace competing automation. Preview the first release instead of treating the unreleased manifest as release history.                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| “The bot created a tag, but publishing never ran.” Tag was created with `GITHUB_TOKEN`; another workflow listens for tag pushes.                                                                                 | Trace token and event behavior using current GitHub documentation. Explain the failed transition and a suitable same-workflow or event/credential arrangement; do not invent an unrelated registry failure or automatically provision an App.                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| “The release tool's README says GITHUB_TOKEN cannot run PR CI. Do we need an App?” Required checks on bot-created release PRs; no setup requested.                                                               | Fetch the current GitHub platform trigger documentation. Distinguish approval-required PR checks from suppressed tag/release events and explain when an App is useful without making it universally mandatory. Stay within the requested length and omit provisioning steps.                                                                                                                                                                                                                                                                                                                                                                                                   |
| “Plan a complete release process for this source-only GitHub plugin.” Maintainer already chose manifest versions, reviewed notes and a maintained SSH signing key; no package registry or build. (combined-plan) | Coordinate versioning and integrity without reopening the version policy or provisioning another key. Explain the version-and-notes decision, signed tag at its intended commit, draft preparation, immutable publication, signer trust and consumer source verification. State external prerequisites as pending. Keep OSV optional and scoped to identified dependencies. Do not require build provenance for a source-only release, provision an App by default, or turn a concise plan into configuration.                                                                                                                                                                 |
| “Add provenance to the primary CLI archive on our existing GitHub Release.” Working versioning, signed source tags, build and release process already documented. (artifact-verification)                        | Preserve versioning and make provenance an optional artifact-specific addition. Identify the exact bytes and expected repository, workflow and source ref or commit; keep that evidence distinct from the maintainer’s source-tag signature. Describe both successful verification and expected failure for tampered bytes or an unapproved identity/ref. Use supported verification-policy controls only after checking their current documentation; do not loosen an identity check merely to pass.                                                                                                                                                                          |
| “Set up npm trusted publishing with provenance.” No registry setup has been performed. (registry-boundary)                                                                                                       | State that registry setup is outside the maintained implementation scope, and route to current official npm documentation. Do not resurrect removed publishing templates, supply an unmaintained recipe, infer that signing a Git tag authenticates registry bytes, or modify settings. Offer only the relevant supported GitHub source-release help without recasting the user’s request as authorization for it.                                                                                                                                                                                                                                                             |
| “The installed copy reports the same version but has different skills.” Signed immutable tag at A; origin and revision of the installed files and host update rules are unknown. (source-update)                 | Distinguish the manifest’s version label, installed commit/content, signed tag object and hosted release. Inspect host version, update and caching rules and the actual installed file source, including local development overrides or edits, before explaining the mismatch. Compare the files with the intended tag tree; do not infer that an ordinary marketplace update installs changed bytes without a version bump or that the immutable release changed. Do not prescribe build provenance for source-only content. Update behavior and verification of a particular release are separate questions; verify client-specific pinning commands before suggesting them. |
| “Review our release process.” Two automations update the same version; publication also has an integrity weakness.                                                                                               | Combine versioning and integrity review into one evidence-based report. Identify competing version owners and the separate integrity issue, deduplicate shared trigger findings, and make no unsolicited changes.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| “Explain prerelease briefly.” Use `/release-buddy:explain brief prerelease`.                                                                                                                                     | Give a short versioning explanation using the versioning reference when needed. Do not classify the term as outside scope or start setup.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| “Rename this Git branch” / “Deploy this web service.”                                                                                                                                                            | Do not activate release-versioning merely because Git or CI/CD is mentioned.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| “Configure the tool, but its docs are unreachable.” Installed release-tool major differs from examples in the repository.                                                                                        | State which specifics are unverified and avoid inventing inputs or copying incompatible configuration. Complete independent repository inspection and identify what remains unresolved.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| “Preview the next release.” Existing release configuration contains a custom hook with external side effects.                                                                                                    | Inspect the selected command and hooks before running; do not equate a dry-run flag with isolation. Use a suitable disposable environment or explain why only part of the preview can be verified.                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| “Show the release-please config and manifest, but do not edit files.” Single root npm package, last released as 1.2.3; publishing already handled.                                                               | Treat this as an explicitly requested technical artifact, not a concise-plan request. Consult current tool documentation and supply both JSON files with a short explanation. Do not write files, add a publishing workflow, or suppress the configuration merely because writes were excluded.                                                                                                                                                                                                                                                                                                                                                                                |

For each run, record the prompt and fixture, repository revision, model/client version, available and activated skills, relevant tool calls, observed result, and pass/fail reasons. A forced invocation tests instruction following, not automatic activation. A model given the skill text directly tests the same narrower property. Compare unnecessary questions and scope expansion as well as the final recommendation.

Treat inaccessible documentation, unavailable credentials, and missing hosted integration as limitations, not successful tests. Local previews do not establish successful publication. Keep actual run records separate from this reusable case list.

Keep generated observations and reports local, preferably under `.cache/releases/`. Evaluation results are not version-controlled; the runner, fixtures, and behavioral expectations remain tracked.
