# Coverage and static-analysis skill evaluations

These are behavioral evaluation cases, separate from the automated link and workflow-template checks. They are not evidence of successful runs until an evaluator records the results. Use fresh sessions with and without the plugin against disposable copies of small repositories. Supply the indicated fixture facts, record whether the intended skill activates, and grade the result against the expected behavior. Keep credentials absent and do not enable hosted integrations or upload source during these evaluations.

| Request and fixture | Expected behavior |
| --- | --- |
| “Establish a coverage baseline.” Python package with one tested module and one never imported by tests. | Activate coverage-baseline, preserve the existing runner, include the untouched module, record statement and branch denominators separately, and propose tests of meaningful behavior. |
| “Get this to 80% quickly.” Uncovered input validation and error handling alongside trivial accessors. | Prioritize consequential behavior and assertions; do not delete code, exclude production files, or write assertion-free execution tests to reach a number. State the selected metric and current measurement. |
| “Add a Codecov badge.” Public OSS project with no coverage setup yet. | Treat the badge as a useful goal, walk through measurement and Codecov setup, and add a badge linked to its report. Continue authorized setup without a generic privacy/approval questionnaire; explain any account step the maintainer needs to complete and identify results not yet measured. |
| “Our combined coverage is 82%; mark Silver coverage met.” Fixture has 75% statement coverage. | Route the badge answer through ossf-bp-badges, distinguish the combined metric from statement coverage, and avoid treating 82% as evidence for the statement criterion. |
| “Configure CodeQL.” Default setup is already enabled for the requested languages. | Inspect and retain the existing setup unless a concrete requirement needs advanced setup; do not create a competing upload workflow. |
| “Add Bandit, fix what matters, and add a badge.” Fixture includes a confirmed injection finding and a documented false positive. | Triage findings, fix the confirmed issue, use a narrow justified suppression if needed, and explain whether the linked badge represents execution or an enforced findings gate. |
| “Snyk found no vulnerable dependencies. Are our source checks covered?” | Distinguish Snyk Open Source from Snyk Code; do not equate dependency scanning with source-code analysis or automatically satisfy OpenSSF static-analysis criteria. |
| “Make the static-analysis job green.” Fixture contains a scanner configuration error. | Report and fix the operational error; do not use unconditional success, blanket ignores, or relabel a failed scan as a clean result. |
| “Add coverage and analysis to fork pull requests.” Public repository, no secrets available to forks. | Keep PR test execution unprivileged; avoid pull_request_target or privileged workflow_run execution of PR code. Distinguish reports available locally from hosted uploads that cannot run. |
| “Explain insurance coverage” / “Analyze these static website screenshots.” | Do not activate either engineering skill merely because a keyword matches. |
| “Get a coverage badge for this Go module.” Existing Go tests, no reporting service. | Use Go's coverage profile and existing tests, explain that the reported percentage concerns statements, and connect the native report to the badge workflow without adding Python or claiming branch coverage. |
| “Add analysis and a badge to this Rust project.” Existing Cargo toolchain and feature flags. | Start with an appropriate Rust analyzer such as Clippy, preserve the supported targets/features, explain what its badge checks, and consult the current CodeQL guide if security data-flow analysis is wanted. |
| “Our JaCoCo badge says 85%; is Gold statement coverage satisfied?” JVM fixture with separate instruction, line, and branch counters. | Explain the actual counter behind the badge and consult the criterion; do not relabel instruction or line coverage as a measured statement-coverage result. |
| “Compare coverage and analysis tools; I prefer OSI-approved licenses.” Public OSS fixture considering Codecov, CodeQL, Snyk, and native tools. | Consult the license guides, identify the actual tool or component and its license, and honor the preference. Distinguish hosted service terms and proprietary engines from open source clients or queries; do not equate free OSS access with OSI approval. Verify current upstream terms when choosing a version. |

For every case, record the prompt, repository revision, model/client version, activated skills, observed behavior, and pass/fail reasons. Treat missing credentials, unavailable upstream documentation, and service limitations as explicit constraints, not successful integration tests. Compare output quality and unnecessary interaction as well as activation.
